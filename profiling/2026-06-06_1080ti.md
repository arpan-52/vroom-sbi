# GPU on-the-fly profiling — 1080 Ti baseline

Date: 2026-06-06
Branch: gpu-online-training
Purpose: sanity/throughput check of the online (GPU on-the-fly) training path on
local hardware before renting an A100.

## Hardware

```
0, NVIDIA GeForce GTX 1080 Ti, 11264 MiB
1, NVIDIA GeForce RTX 2060, 6144 MiB
```
All runs pinned to the **1080 Ti** via `CUDA_VISIBLE_DEVICES=1` (Pascal sm_6.1,
11 GB, FP32-only — no Tensor Cores / TF32).

## Environment

- pixi env: `gpu-dev` (feature `gpu`: conda-forge `pytorch-gpu`, system-requirements cuda 12)
- torch 2.11.0, CUDA available: True
- Profiler: `torch.profiler` (CPU+CUDA activities), warmup excluded.
- Harness: `src/utils/profiling.py::profile_online_training`
- Flow: NSF (config defaults), embedding `SpectralEmbedding`, model faraday_thin.

## Read of the numbers

- **Generation cost is negligible: 1.9–6.0% of compute** (2.7–8.7 ms/step). The
  GPU on-the-fly source is not the bottleneck; inline generation is sufficient
  (no CUDA-stream double-buffering needed). `generate_batch` self-CUDA is
  ~2.6 ms/step.
- **Memory is tiny: 283–523 MB** even at 4096 ch. Enormous headroom on 11 GB —
  batch size can grow ~20–30x, which matters for A100 utilization.
- **Step time is dominated by the NSF flow** (aten::mm / addmm / *Backward), not
  by our generator. The `maxwell_sgemm_64x64` kernel is the tell: these are slow
  legacy FP32 GEMMs. The 1080 Ti has no Tensor Cores and no TF32, so every
  matmul runs at plain FP32 throughput (~11 TFLOPS).
- `aten::nonzero` / `index_put` / `IndexBackward` are inside nflows' spline
  transform, not our augmentation (our `generate_batch` is 2.6 ms total).
  `nonzero` is a synchronizing op — a real per-step overhead, but it lives in
  the flow library.

## Why the per-step time looks bad, and the A100 expectation

The 1080 Ti is the worst case for this workload: FP32-only Pascal. The flow is
matmul-bound, so it cannot use the hardware that makes an A100 fast. Expected
A100 gains: TF32 tensor-core GEMMs (≈8–16x on the matmuls), ~5x memory
bandwidth, and far better large-batch scaling. Combined with a 20–30x larger
batch (memory allows it), throughput per dollar should be very different.

**Conclusion:** the architecture holds — generation is free and memory is a
non-issue at full band. The current per-step cost is a 1080 Ti FP32 artifact,
not a design flaw. Worth confirming on A100 before scaling, with: (a) larger
batches, (b) TF32 enabled (`torch.set_float32_matmul_precision('high')`),
(c) optional AMP/bf16 for the flow.
